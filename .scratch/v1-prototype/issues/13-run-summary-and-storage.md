# 13: สรุปการวิ่ง คะแนนฟอร์ม และบันทึกลงเครื่อง

**Blocked by:** 06, 12

**Status:** done

## What to build

ผู้ใช้กดจบการวิ่งแล้วเห็นหน้าสรุปที่มีระยะทาง เวลา pace เฉลี่ย แคลอรี สถิติแยกรายกิโลเมตร แผนที่เส้นทางที่วิ่ง และ FormScore เป็นประโยคที่บอกว่าฟอร์มเป็นยังไงและควรทำอะไรต่อ

Session ถูกบันทึกลงเครื่องด้วย expo-sqlite ทันทีที่จบ และเปิดดูซ้ำได้แม้ปิดแอปไปแล้วหรือไม่มีอินเทอร์เน็ต ดู ADR 0003

การเขียนลงเครื่องต้องเกิดก่อนเสมอ ไม่มีอะไรในแอปนี้ที่ต้องรอเน็ตถึงจะบันทึกได้

## Acceptance criteria

- [x] หน้าสรุปแสดงระยะทาง เวลา pace แคลอรี และ splits รายกิโลเมตร
- [x] แสดง FormScore เป็นประโยคที่บอกสิ่งที่ควรทำต่อ
- [x] แสดงแผนที่เส้นทางที่วิ่งมา
- [x] Session ถูกบันทึกลงเครื่องและเปิดดูซ้ำได้หลังปิดเปิดแอป
- [x] บันทึกสำเร็จแม้ปิดอินเทอร์เน็ต (ไม่มี network call ใดเลยในเส้นทางจบวิ่ง→บันทึก→หน้าสรุป)
- [x] Session ที่สั้นเกินไปแสดงว่าข้อมูลไม่พอสำหรับประเมินฟอร์ม (แยกข้อความจากกรณี "ไม่มีข้อมูล cadence" ด้วย — สองสาเหตุคนละเรื่องกัน)

## หมายเหตุ (เพิ่มระหว่างตั๋ว 12)

ตั๋ว 12 พบว่า cadence จาก accelerometer บนแอนดรอยด์ 12 ขึ้นไปถูกวัดต่ำกว่าจริงเสมอที่จังหวะวิ่งทั่วไป
(160-190 ก้าว/นาที) และยิ่งจังหวะเร็วยิ่งถูกกดต่ำกว่าจริงมากขึ้น (ขีดจำกัด Nyquist ของอัตราสุ่มตัวอย่าง
200ms ที่ระบบบังคับ ดู services/step-detector.ts) ก่อนเชื่อม `hooks/use-cadence-sensor.ts`'s `samples`
เข้ากับ `evaluateFormScore` (ตั๋ว 06) ต้องคิดว่าความไม่สมมาตรนี้จะกลบสัญญาณ cadenceDropped จริงหรือไม่
เช่น วิ่งจริงจาก 190 ตกเหลือ 170 ช่วงท้าย อาจวัดได้ออกมาใกล้เคียงกันเพราะทั้งคู่โดนกดต่ำกว่าจริงคนละ
ระดับ ยังไม่มีทางแก้ที่ชัดเจนในตอนนี้ อาจต้องแจ้งผู้ใช้ตรง ๆ ว่า cadence เป็นค่าประมาณ หรือลดน้ำหนัก
สัญญาณนี้ลงเมื่อคำนวณ FormScore แทนที่จะเชื่อว่าแม่นเท่าที่ตั๋ว 06 ตั้งใจไว้แต่แรก

## หมายเหตุ (ปิดตั๋ว)

### วิธีแก้ความกังวลข้างบน: บอกตรง ๆ ไม่ใช่ปรับตัวเลข

เลือก "แจ้งผู้ใช้ตรง ๆ" ไม่ใช่ "ลดน้ำหนักสัญญาณ" เพราะทิศทางของความคลาดเคลื่อนไม่แน่นอน (ขึ้นกับ
จังหวะจริงเทียบกับจุดที่ตัวอย่าง accelerometer ตกตรงไหนพอดี) การเดาสูตรลดน้ำหนักโดยไม่มีข้อมูลจาก
เครื่องจริงมายืนยัน เสี่ยงสร้างความเอนเอียงใหม่ที่ไม่รู้ทิศทางเหมือนกัน แทนที่จะแก้ปัญหาจริง `core/coach/form-score.ts` เลยไม่ถูกแตะเลย (ตรรกะถูกต้องอยู่แล้ว **ถ้า**ป้อนตัวเลขที่แม่น) `services/form-samples.ts`
จัดการเฉพาะกรณี "ไม่มีข้อมูล cadence เลย" (ข้อความคนละอันจากกรณี "สั้นเกินไป" อย่างจงใจ มีเทสต์ยืนยัน)
ส่วนกรณี "มีข้อมูลแต่ตัวเลขอาจเอนเอียง" ซึ่งเป็นเรื่องที่หมายเหตุด้านบนกังวลจริง ๆ แก้ที่ชั้น UI แทน
(`app/run-summary.tsx`) ด้วยประโยคกำกับเสมอเมื่อ FormScore ตัดสินจริง (`hasEnoughData: true`) ว่า
คำนวณจากเซนเซอร์ที่อาจคลาดเคลื่อนที่จังหวะเร็ว ใช้เป็นแนวทางคร่าว ๆ ไม่ใช่ค่าที่แม่นยำสมบูรณ์

### บั๊กจริงที่เจอและแก้ระหว่างรีวิว (สองแกน)

- **timestamp คนละนาฬิกากันระหว่าง cadence กับ GPS** — เจอเองระหว่างเขียนโค้ด ก่อน commit เลย
  `location.timestamp` ของ expo-location เป็น Unix epoch จริง (ยืนยันจาก type declaration) แต่
  timestamp ของ accelerometer บนแอนดรอยด์นับจากตอนเปิดเครื่อง ไม่ใช่ Unix epoch ถ้าเทียบสองนาฬิกานี้
  ตรง ๆ ตอน join (`buildFormSamples`) จะได้ผลผิดทั้งหมด แก้โดยให้ `use-cadence-sensor.ts` ยังใช้นาฬิกา
  เซนเซอร์เองสำหรับคำนวณ cadence ภายใน (แม่นกว่า ไม่มี bridge jitter) แต่ใช้ `Date.now()` เฉพาะตอน
  ปล่อยค่าออกไปให้ข้างนอกใช้ต่อ
- **`storage/session-storage.ts` เปิดฐานข้อมูลล้มเหลวครั้งเดียวแล้วค้างตลอดไป** — แคช Promise ไว้ใน
  ตัวแปรโมดูล เดิมไม่ล้างแคชเมื่อ reject ทำให้ error ครั้งแรกทำให้ทุกการเรียกถัดไปพังซ้ำเดิมตลอดไป
  (ขัดกับ UX "ลองกดจบการวิ่งอีกครั้ง" ที่สร้างไว้ใน live-run.tsx โดยตรง) แก้โดยล้าง `dbPromise = null`
  ใน `.catch` ก่อน rethrow ให้เรียกใหม่ได้จริง
- **เวลาที่บันทึกอาจคลาดเคลื่อนได้ถึง 1 วินาทีทุกครั้ง** — `useLiveRunTracker.finish()` เดิมไม่คืนค่า
  วินาทีที่แม่นยำ ผู้เรียกอ่าน `tracker.elapsedSeconds` จาก state ต่อในซิงโครนัสเดียวกัน ซึ่งยังไม่ทัน
  อัปเดตจาก setState แบบ async ข้างใน ก่อนตั๋วนี้ไม่มีใครสังเกตเพราะเป็นแค่ตัวเลขจอที่รีเฟรชเองในเฟรม
  ถัดไป แต่ตอนนี้ค่านี้ถูกบันทึกลง SQLite ถาวรตอนกดจบพอดี ความคลาดเคลื่อนเลยติดอยู่ในข้อมูลตลอดไป
  แก้โดยให้ `finish()` คืนวินาทีที่แม่นยำตรง ๆ แล้วคำนวณ pace ใหม่จากค่านั้นก่อนบันทึก

ทั้งสองบั๊กหลังพบจาก subagent รีวิวสองแกน ไม่ใช่จากเทสต์อัตโนมัติ (เกี่ยวข้องกับ closure timing และ
Promise caching ซึ่งเทสต์แบบ unit ปกติไม่ครอบคลุม)

### ยังไม่เคยทดสอบกับเครื่องจริง

expo-sqlite, การบันทึกจริง, แผนที่เส้นทางย้อนหลังใน run-summary.tsx (โดยเฉพาะ `fitToCoordinates` ผ่าน
`onMapReady`) ยังไม่เคยรันบนอุปกรณ์จริงเลยในสภาพแวดล้อมนี้ ตรวจสอบแล้วด้วย typecheck + เทสต์ (181 ผ่าน)
+ lint + bundle-compile เท่านั้น ต้องทดสอบซ้ำบนเครื่องจริงก่อนนำเสนอ
